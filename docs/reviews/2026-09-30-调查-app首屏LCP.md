# 调查：/app 首屏 LCP 落后 FCP 约 38 秒

- 调查日期：2026-09-30
- 目标页面：https://hk.apks.cc/app （本地等价物 http://127.0.0.1:3002/app，生产 `next start`）
- 调查性质：性能缺陷调查（先证伪，再谈修）
- 结论强度：**高**。全部结论基于真实 Chromium + CDP 实测，非源码推断。

---

## 0. 结论摘要

| # | 问题 | 结论 |
|---|------|------|
| A | LCP 元素是什么 | **是一个文本块 `<p>`，不是任何图片。** 位于 `src/app/app/page.tsx` 顶部介绍区的简介段落，属于首屏 SSR HTML。`loadTime = 0`，与图片加载无关。 |
| B | 38 秒落差成因 | **是 20 倍 CPU 降速下的测量伪影，不是 LCP 缺陷。** 真实成因是主线程饱和（1.83 MB gzip JS + React hydration）。1x / 4x / 8x 降速下 `LCP - FCP` 恒为 **0**；只有 20x 才出现，且随降速倍率单调放大。 |
| C | `unoptimized: true` 的后果 | **真实存在且已量化。** `sizes` 完全失效（服务端 HTML 里 `srcset` 数为 0）。/app 引用 22 张唯一图片共 **8.6 MB**，其中 9 张是 2560x1440。但任务书设想的修法（`getPreviewImageUrl`）对 `cdn.apks.cc` **是空操作**，且该 CDN 不支持任何查询参数缩放。→ 属基建决策，只报告。 |
| D | 首屏是否该加 `priority` | **不该加。** Next 15.0.7 中 `priority` 并未废弃（见 §6.1）；但 LCP 是文本，加 `priority` 对 LCP 零收益，且 13 个 `<link rel=preload>` 会与 1.83 MB JS 争抢带宽，**是净劣化**。 |

**一句话**：38 秒落差不存在为可修缺陷，它是一个只在 20 倍降速下才出现的合成伪影。真正值得处理的是另外两件事——**8.6 MB 未缩放图片**和 **1.83 MB gzip JS**——两者都需要基建/产品拍板，本轮不实施。

**本轮未修改任何业务代码。** 工作区唯一变更是新增本报告文件。

## 1. 调查方法与工具

### 1.1 工具选型

- **没有安装 playwright，也没有 `pnpm add` 任何依赖。**
- 环境已有 Playwright 下载的 Chromium 二进制：`C:UsersAdministratorAppDataLocalms-playwrightchromium-1243chrome-win64chrome.exe`。
- Node 24 自带全局 `WebSocket`，因此直接用 **CDP over WebSocket** 驱动真实 Chromium，零新增依赖。
- 测量脚本与探针全部写在 `D:Tempcprobe`（系统临时目录），**工作区内零探针文件**；用完已删除。

### 1.2 测量方法

- 每次运行新建独立 `--user-data-dir`（冷缓存），headless new 模式。
- 通过 `Emulation.setCPUThrottlingRate` 施加 CPU 降速；通过 `Network.emulateNetworkConditions` 施加 Fast 3G（1.6 Mbps / 150 ms RTT，与 Lighthouse 移动默认一致）。
- `Page.addScriptToEvaluateOnNewDocument` 在导航**之前**注入 `PerformanceObserver`，对 `largest-contentful-paint`（`buffered: true`）、`paint`、`layout-shift`、`longtask` 全程记录。
- **LCP 元素在 observer 回调当场快照**（`tag`、`className`、`currentSrc`、`naturalWidth/Height`、`loading`、`fetchpriority`、`srcset`、`getBoundingClientRect()`），避免事后取错元素。
- LCP 收敛判定：轮询至 LCP 连续 15 秒无变化，或达到 settle 上限。
- 另取 `Performance.getMetrics`（TaskDuration / ScriptDuration / LayoutDuration / RecalcStyleDuration / Nodes）。

### 1.3 已知环境噪声（重要）

测量期间机器上有**另一个 headless Chrome 实例在跑**（`C:\Program Files\Google\Chrome\Application\chrome.exe --headless --remote-debugging-port...`），推测来自并行的审计线。因此本报告**只做同机相对比较**，不把绝对毫秒数当作真机结论。绝对值波动见 `domInteractive` 在两次 20x 复现中为 79.7s 与 107.2s——但**落差的符号与归因在所有运行中一致**。

## 3. 问题 A：LCP 元素到底是什么？

### 3.1 答案

**是一个文本块 `<p>`，而且在所有 11 次运行中无一例外。**

- 元素：`P`，class `mt-3 max-w-3xl text-sm leading-6 text-muted-foreground`
- 位置：`src/app/app/page.tsx` 中 `<section className="mb-8 rounded-2xl border bg-card p-6 shadow-sm">` 里的简介段落（`siteName + " 游戏库收录热门安卓游戏……"`）
- 桌面视口下 painted 尺寸 768x48，LCP size = 33352
- 移动视口下 painted 尺寸 330x120，LCP size = 38164
- `loadTime = 0`、`currentSrc = ""`、`naturalWidth = 0` → **不是图片，不涉及任何图片下载**

### 3.2 "一个元素还是多次更新"？——两者都是

`largest-contentful-paint` 的 entry 数量在多次运行中为 1~3 条：

| 运行 | entry 数 | 序列 |
|------|---------|------|
| `app-cpu1-repeat` / `app-cpu4` / `app-cpu8` / 两个 fast3g | 1 | 直接就是那个 `<p>` |
| `base-cpu20-1280` / `app-cpu20-noimg` / `app-cpu20-nojs-clean` / `detail-cpu20` | 2 | 先 header 的 `SPAN`（75x28, size 2233），后 `<p>`（size 33352） |
| `app-cpu20-repeat` / `app-cpu20-nonew` | 3 | 先 header logo `IMG` 28x28（`fetchpriority=high`, nat 512x512, size 784），再 `SPAN`，最后 `<p>` |

解读：**LCP 发生了更新，但更新方向是"越来越大"，且最终候选是一个早已存在于首屏 SSR HTML 的文本节点。** 首条 entry 只是首屏最早被画出来的 header 区域，它比后续的 `<p>` 面积小，于是被替换。**没有任何一次更新是"某个大元素被重绘/变大"**——每次都是不同元素依次成为"当前最大"。

### 3.3 任务书硬事实 #8 的文件指向有误（但结论仍成立）

任务书说 `src/components/game-card.tsx:22-30` 的 `<Image>` 没有 `priority`。实测：

```
rg -n "game-card" src/
  src/app/profile/ProfileDashboard.tsx:12
  src/app/profile/center/games/page.tsx:11
```

**`GameCard`（game-card.tsx）只用在 /profile/* 两个页面，/app 根本不用它。**
/app 真正的卡片是 `src/app/app/AppLibraryView.tsx:285` 的 `LibraryGameCard`，其 `<Image>` 在 **line 305**，同样没有 `priority` / `fetchPriority` / `loading`。

所以任务书的**机制结论（无 priority → 输出 loading="lazy"）依然成立**，只是引用错了文件。真正需要改（如果改的话）的是 `AppLibraryView.tsx:305`，不是 `game-card.tsx`。

### 3.4 为什么 /app 首屏根本没有图片候选？

首屏截图（1280x800，测量时抓取、随探针一并删除）：整屏只有 header + 介绍区 + 左侧分类栏 + 筛选面板，**游戏卡片网格完全在折叠线以下**。

首屏截图（412x823 移动端，测量时抓取、随探针一并删除）：整屏只有 header + 介绍区，**同样一张卡片 banner 都没有**。

数据佐证：`app-fast3g-nocpu` 运行中，`imageCount = 1`，而那唯一一张图是 `https://hm.baidu.com/hm.gif`（百度统计像素）。**首屏一张 banner 都没加载。**

因此在 1280x800 与 412x823 两个视口下，/app 的首屏 LCP **在结构上就不可能是图片**。这解释了为什么任务书列的三组 Fast 3G / 详情页数据都呈现 FCP==LCP 或小落差。

## 4. 问题 B：38 秒落差的成因是什么？

### 4.1 结论

**是 20 倍 CPU 降速下才出现的合成伪影，不是 LCP 缺陷。** 三个候选假设逐一排除：

| 假设 | 判定 | 反证 |
|------|------|------|
| 图片懒加载晚到 | **排除** | 屏蔽**全部**位图后（`app-cpu20-noimg`），LCP 元素仍是同一个 `<p>`，`loadTime` 仍为 0，落差仍有 12184 ms。图片从头到尾没参与过 LCP。 |
| hydration 后重渲染触发大元素重绘 | **排除** | 全部 11 次运行 `layout-shift` 总量为 **0**（最大 0.0001）。没有布局位移，就没有"元素变大/换位导致重绘"。且被屏蔽 JS chunk（无 hydration）的运行里，落差依然存在 8052 ms。 |
| 20 倍降速下的测量伪影 | **成立** | 1x / 4x / 8x 下 `LCP - FCP` 恒为 **0**；只有 20x 才出现，且随倍率单调放大。见 §4.2。 |

### 4.2 决定性对照：落差随降速倍率单调放大

```
CPU 1x  : FCP 1628  LCP 1628   gap 0
CPU 4x  : FCP 2620  LCP 2620   gap 0
CPU 8x  : FCP 7360  LCP 7360   gap 0
CPU 20x : FCP 14436 LCP 45056  gap 30620
CPU 20x : FCP 8660  LCP 37560  gap 28900
CPU 20x : FCP 6272  LCP 33860  gap 27588
```

**`app-cpu8` 是最有力的对照**：该运行 `domInteractive = 20172`、长任务 16 个共 19887 ms——也就是说 8 倍降速下**主线程已经饱和、可交互要等 20 秒**了，但 `FCP` 与 `LCP` **分毫不差地相等（都是 7360）**。

这说明：主线程饱和本身**并不**自动产生 FCP/LCP 落差。落差需要"降速倍率高到渲染管线被迫渐进式地、一段一段地往下画"才会出现。真实设备的降速倍率落在 4x~8x 区间（对应中低端安卓机），**落差不成立**。

### 4.3 真实成因：主线程饱和

20x 下的 `domInteractive` / `load`：

```
CPU 1x  : domInteractive 853     load 1348
CPU 4x  : domInteractive 5722    load 5739
CPU 8x  : domInteractive 20172   load 20237
CPU 20x : domInteractive 79700   load 79779
CPU 20x : domInteractive 107194  load 107367
```

而 `Performance.getMetrics` 显示该页**真实**的主线程成本是秒级的：

```
TaskDuration 5~10 s / ScriptDuration 1~5 s / LayoutDuration 2 s / Nodes 4999
```

×20 之后正好落在 80~140 秒量级，与观测到的 `domInteractive` 完全吻合。

**因果链**：
1. /app 首屏内联 295 KB HTML + 21 个内联 RSC flight 块 + **1.83 MB gzip JS**（5 个 chunk，其中首页 chunk `app/page.js` 597 KB 被硬加载）。
2. 20 倍降速下，解析 + 编译 + 执行 + hydration 把主线程占满约 80~140 秒。
3. 渲染器在长任务的间隙里**渐进式**绘制：先画出 header 的 `SPAN`（14.4 s），再往下推进到介绍区段落（45.1 s）。
4. 段落成为 LCP 候选的时刻 = 主线程刚好推进到那里并完成绘制的时刻，于是 `LCP` 落在 45 s。
5. **"LCP 比 FCP 晚 38 秒"只是"主线程推进到文档中部所需时间"的重述。**

### 4.4 定向验证：去掉 hydration 后落差大幅缩水

```
条件                        domInteractive   FCP    LCP    gap
20x 正常（含 hydration）      79700 / 107194  14436  45056  30620
20x 屏蔽 JS chunk（无 hydration）58676          7352   15404   8052
```

屏蔽 hydration 后落差从 ~30 s 掉到 ~8 s（约 1/4）。**主因是 JS 解析执行 + hydration，不是图片、不是布局重排。**

注：`domInteractive` 即使在零 JS 时仍高达 58.7 s，这说明在 20 倍降速下**单纯的 HTML 解析 + 样式 + 布局 + 图片解码**同样极慢。但即便如此，落差也只有 8 s——再次印证落差是"降速倍率"而非"某元素"造成的。

### 4.5 任务书硬事实 #2 / #3 的复核

| 任务书说法 | 本次实测 | 判定 |
|-----------|---------|------|
| #2 详情页 FCP 10180 / LCP 10180（完全相等） | `detail-cpu20`: FCP 7504 / LCP 13140，**gap 5636** | **不成立**。详情页在 20x 下同样有落差，只是小得多（5.6 s vs 30.6 s）。 |
| #3 /app Fast 3G 下 FCP 6860 / LCP 6860（相等） | `app-fast3g-nocpu`: 1856/1856；`app-fast3g-cpu4`: 3000/3000，gap 0 | **成立**。且能解释：Fast 3G 跑的是移动视口，首屏无图，LCP 必为文本。 |
| #4 只有 /app 在 20x 这一种条件下出现落差 | 详情页 20x 也有落差（5.6 s） | **部分不成立**。差距是量级差不是有无差。 |

**为什么详情页落差小得多？** 详情页的 LCP 是**首图封面**，一张 `loading="lazy"` 但在视口内、`loadTime=9460` 的图。它一旦解码完成就立刻绘制；LCP 时刻由**图片解码完成**决定，而不是由"渲染器推进到文档中部"决定。/app 的 LCP 是**文档中部偏上的文本**，只能等渲染器一步步推进过去。**这是两者落差量级差异的唯一机制。**

### 4.6 交付口径

- **该 38 秒落差在真实设备上不成立**，请从"缺陷"清单里划掉。
- 1x / 4x / 8x 全部 gap = 0，Fast 3G + 4x（最接近真实低端机的组合）gap = 0。
- 20x 是 Lighthouse 默认 4 倍的 5 倍，属于极端压力档；它测出的是**主线程总成本**，不是 LCP 缺陷。
- 但请注意：**20x 暴露的那个"主线程总成本"本身是真实的**（1.83 MB gzip JS + 4999 个 DOM 节点）。它是可优化项，但不是本轮任务定义的那个"LCP 缺陷"，且优化手段超出"纯性能属性"范围。→ 见 §8.4。

## 5. 问题 C：`unoptimized: true` 的已存在后果

> 前提遵守：`unoptimized` 是有据可依的既有决策（`next.config.ts:81-83` 注释：绕过 Next 图片优化器，避免上游超时拖垮开发态与生产）。**本报告不建议翻转它。**

### 5.1 `sizes` 是否完全失效？——是，已证实

`unoptimized: true` 时 Next 不生成 `srcSet`，因此 `sizes` 属性没有任何协商对象。服务端 HTML 实测（§2.4）：

- `srcset` 出现次数：**0**
- `fetchpriority` 出现次数：**0**
- `<img>` 总数 46，其中 **45 个 `loading="lazy"`**

PerformanceObserver 抓到的 LCP 元素快照里 `srcset: ""`，同样印证。

**后果**：每台设备——包括 375px 宽的手机——都下载**原图**。

### 5.2 量级后果

/app 引用 22 张唯一图片，共 **8637 KB**，其中 9 张宽度 2560（`blinko` 类文件名自带 `-w2560-h1440-r.webp` 尺寸后缀）。

首屏卡片实际显示宽度：
- 1280x800 视口：`xl:grid-cols-4`，卡片约 **300px** 宽
- 412x823 视口：`grid-cols-1`，卡片约 **380px** 宽

即：**为 300~380 px 的显示区域下载 2560 px 宽的图，横向超采样约 7~8 倍。** 最大单张 3 MB。

`/app` 首屏虽不展示卡片（§3.4），但用户**向下滚动一屏**就会开始加载这些图，8.6 MB 是滚动路径上的真实成本。**这是本轮唯一被证实为"真缺陷"的项。**

### 5.3 任务书设想的修法可行性评估：`getPreviewImageUrl` 路线 —— 不可行

任务书建议"用既有的 `getPreviewImageUrl` 之类 helper 走上游 CDN 自带尺寸参数"。逐条核对 `src/lib/image-preview.ts`：

```ts
const GOOGLE_PLAY_IMAGE_HOST = 'play-lh.googleusercontent.com';
const WEBP_VARIANT_HOSTS = new Set(['tc-new.z.wiki', 'img.pagehost.cn']);

export function getPreviewImageUrl(input, width) {
  // 1) 命中 play-lh.googleusercontent.com -> 改写为 =w{width}-rw
  // 2) 命中 WEBP_VARIANT_HOSTS 且路径以 .jpg/.png 结尾 -> 追加 /webp
  // 3) 其余 -> return raw（原样返回）
}
```

**覆盖情况：**

| 图源 | /app 是否在用 | `getPreviewImageUrl` 是否生效 |
|------|--------------|--------------------------|
| `play-lh.googleusercontent.com` | **否**（详情页图标/截图在用） | 生效 |
| `tc-new.z.wiki` / `img.pagehost.cn` | 否 | 生效（仅补 `/webp`） |
| `cdn.apks.cc/uploads/*.webp` | **是**（多数卡片） | **不生效，原样返回** |
| `cdn.apks.cc/blinko/*`（无扩展名） | **是**（9 张 2560px 大图） | **不生效**（WEBP_VARIANT_HOSTS 不含该 host） |

/app 的 22 张图**全部**落在 `cdn.apks.cc`，而 `cdn.apks.cc` **既不在 `GOOGLE_PLAY_IMAGE_HOST` 也不在 `WEBP_VARIANT_HOSTS`**。→ **对 /app 而言，`getPreviewImageUrl` 是彻底的空操作。**

仓库既有测试已经把这条约束固化了：

```
✔ 未知图源、相对地址和无效宽度保持原地址
✔ 非 Google Play 图源不生成响应式候选
```

### 5.4 更硬的反证：CDN 本身不提供查询参数缩放

即便绕过 helper 直接拼参数，也不行（§2.6 实测）：`?w=320`、`?width=320`、`?imageView2/1/w/320`、`?x-oss-process=image/resize,w_320` 全部返回**字节完全一致的 62500 字节**原图。响应头 `Server: cloudflare`、`cf-cache-status: DYNAMIC`，但未启用 Image Resizing 变换。

**结论：`unoptimized` 导致的 `sizes` 失效是真缺陷，但当前图源（`cdn.apks.cc`）不具备任何服务端缩放能力，`getPreviewImageUrl` 路线对本页 100% 无效。** 真正可用的三条路都需要拍板，见 §10。

## 6. 问题 D：首屏是否应有 `priority` / `fetchPriority="high"`？

### 6.1 以 `node_modules/next` 实际实现为准（next@15.0.7）

任务书要求不要凭印象。以下全部来自 `node_modules/.pnpm/next@15.0.7_.../node_modules/next/dist/`：

**(a) 无 `priority` 时确实输出 `loading="lazy"`** —— `shared/lib/get-img-props.js`

```js
// :225
let isLazy = !priority && (loading === 'lazy' || typeof loading === 'undefined');
// :429
loading: isLazy ? 'lazy' : loading,
```

**(b) `priority` 并未废弃** —— 同文件 `:352`，Next 自己的 LCP 警告文案仍在劝你加它：

```js
warnOnce('Image with src "' + lcpImage.src + '" was detected as the Largest Contentful Paint (LCP). ' +
         'Please add the "priority" property if this image is above the fold. ...')
```

**(c) `priority` 干两件事，`fetchPriority` 只干一件**

```js
// client/image-component.js:294 —— priority 会额外注入 <link rel="preload">
imgMeta.priority ? jsx(ImagePreload, { isAppRouter, imgAttributes }) : null

// shared/lib/get-img-props.js:430 —— fetchPriority 只是原样透传成属性
fetchPriority,
```

React 19 下走 camelCase（`image-component.js:120-132`），React 18 下走小写 `fetchpriority`。

**(d) 二者不可并用 lazy** —— `:290`：同时给 `priority` 和 `loading="lazy"` 会直接 `throw`。

### 6.2 正确用法与优先级顺序（Next 15.0.7）

```
想要 <link rel=preload> + 取消 lazy：  用 priority
只想要改变下载优先级（仍是 lazy）：      用 fetchPriority="high"
仓库现有约定：                           priority + fetchPriority="high" 成对出现
```

**结论：`"Next 13+ 推荐 fetchPriority，priority 已废弃"` 这个说法在 15.0.7 上不成立。** 本仓库版本下 `priority` 仍是唯一能同时关闭 lazy 并注入 preload 的属性，且 Next 官方文案仍在推荐它。

### 6.3 /app 首屏该不该加？——不该，四条理由

1. **对 LCP 零收益**：LCP 是文本 `<p>`（§3.1）。提升图片优先级不会让文本 LCP 变快。
2. **首屏没有图可提升**：1280x800 与 412x823 下 `<img>` 首屏数量为 0（§3.4）。加 `priority` 是给折叠线以下的图插队。
3. **会净劣化**：每个 `priority` 注入一条 `<link rel=preload>`。给 13 张卡片都加上 = 13 条 preload 去和 1.83 MB JS 抢带宽，**直接拖慢 hydration**，而 hydration 正是 §4.3 认定的主因。
4. **违反仓库既有约定**：现有代码只在**单张 lead 图**上加高优先级——
   - `src/components/home/HomeHeroCarousel.tsx:363-364` → `priority` + `fetchPriority="high"`
   - `src/components/community/CommunityPostCard.tsx:572-573, 601-602` → `priority` + `fetchPriority`（仅 `isLeadImage`）
   - `src/components/game-carousel.tsx:169` → `priority={index === 0}`
   - `src/components/albums/AlbumTopicView.tsx:627` → `priority`

   `LibraryGameCard` 不给任何卡片加 `priority`，与该约定一致，**不是遗漏**。

### 6.4 详情页对照组（为什么详情页加了也没救）

`detail-cpu20` 的 LCP 图 `loading="lazy"`、`fetchpriority=null`，`loadTime=9460` / `renderTime=13140`。给它加 `priority` 最多把 9.5 s 的图片下载提前，**但主线程在 20x 下 137 秒才可交互**，preload 抢不过 hydration。→ 同样印证 §6.3.3。

> 注：仓库已有守护测试 `首屏样式确定且非首屏截图不声明高优先级`，说明"只给首屏图加高优先级"是被测试固定的设计意图。

## 8. 修法论证与风险

### 8.1 "给 /app 卡片加 priority / fetchPriority"

- **收益**：0（LCP 是文本，首屏无图）。
- **风险**：13 条 `<link rel=preload>` 与 1.83 MB JS 争带宽，拖慢 hydration；违反仓库"仅 lead 图"约定；可能触发 `priority` + `loading="lazy"` 冲突抛错。
- **判定：不做。** 这是把问题变严重。

### 8.2 "用 `getPreviewImageUrl` 给 /app 卡片缩图"

- **收益**：0。helper 对 `cdn.apks.cc` 是空操作（§5.3），CDN 也不认查询参数（§5.4）。
- **风险**：无技术风险，但**零效果**，属于"看起来在修、实际没修"。
- **判定：不做。** 典型陷阱：数字会变好看（代码更"规范"），但机制讲不通。

### 8.3 "翻转 `unoptimized: false`"

- **收益**：`sizes` 恢复协商，8.6 MB 可降到 1 MB 量级。
- **风险**：正是 `next.config.ts:81-83` 注释要规避的上游超时；且 `cdn.apks.cc` 需被 `remotePatterns` 放行，属于**推翻既有决策**。
- **判定：不建议单方面执行。** 需 §10 拍板。

### 8.4 "削减 /app 的 JS 负载"

- **收益**：直击 §4.3 认定的真实主线程成本。首页 chunk `app/page.js`（597 KB gzip）作为硬 `<script>` 出现在 /app 上，收益空间明确。
- **风险**：涉及路由拆分 / 动态 import / `next.config` 调整，**不属于"纯性能属性"**，改动面大且可能影响导航体验。
- **判定：超出本轮红线，只报告。**

### 8.5 "把介绍区段落移出首屏"或改布局

- 会改变页面呈现内容。
- **判定：红线，不实施。**
