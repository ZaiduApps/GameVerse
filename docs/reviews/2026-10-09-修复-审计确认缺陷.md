## 2. B1 帖子发布时间取了最后回复时间

### 2.1 确认事实（审计结论成立）

修前 `src/lib/community-api.ts:364-366`：

~~~text
364:  const rawTimestamp = normalizeRawTimestamp(
365:    item.last_commented_at || item.publish_at || item.created_at,
366:  );
~~~

链路：`community-seo.ts:76` 的 `published = String(post.rawTimestamp || '').trim()` → `community-seo.ts:172-173` 的 `datePublished`，以及 `src/app/community/post/[id]/page.tsx:85` 的 `openGraph.publishedTime`。所以任何有过回复的帖子，`datePublished` 输出的是最后回复时间。

### 2.2 publish_at 与 created_at 的语义判断依据（动手前确认）

| 证据 | 结论 |
|---|---|
| 类型层：`ApiCommunityPost` 分别声明 `publish_at / last_commented_at / created_at / updated_at`（`community-api.ts:70-73`） | 四个字段是四种独立语义，不是同义别名 |
| 后端写入：`content.service.ts:1541-1544` 接受请求体显式传入 `publish_at`（非法值报错）；`:1642-1644` 上线 / 审核通过时 `if (!payload.publish_at) payload.publish_at = new Date()`；`:4881-4892` 同一逻辑 | `publish_at` = 「确定发布」的时刻，可由运营指定，缺省取发布动作发生时间 |
| 后端排序：默认最新流是 `{ publish_at: -1, created_at: -1, _id: -1 }`（`content.service.ts:1929`）；热门流 `{ like_count: -1, comment_count: -1, publish_at: -1, _id: -1 }`（`:1913`）；只有 `sort=latest_reply` 才把 `last_commented_at` 放首位（`:1914-1920`） | 后端自己就把 `publish_at` 当「发布时间」的排序键，把 `last_commented_at` 当「回复活动时间」的排序键 |
| `created_at` 只作为 `publish_at` 的次选排序键（`:1929`）与 `$ifNull: ["$publish_at", "$created_at"]` 兜底（`:493`） | `created_at` 是文档创建时间，语义弱于 `publish_at`，只能排第二顺位 |

结论：`publish_at || created_at || last_commented_at` 是正确的优先序，任务给定的改法与后端语义一致。

### 2.3 改了什么

`src/lib/community-api.ts:368-370`（现）：

~~~text

369:    item.publish_at || item.created_at || item.last_commented_at,
370:  );
~~~

- 只翻转取值优先级，并补注释说明四个时间字段的语义。
- **未改** `updated_at` → `updatedAt`（`:371`）与 `community-seo.ts:77` 的 `modified` 链路。
- **未改** `:384-386` 生成可见「x 小时前」的 `timestamp`：它与 `rawTimestamp` 是两处独立表达式。审计 6.2 已确认 `timestamp` 的原始语义是「最近活动时间」，卡片文案按活动时间展示属既有交互形态，改它等于改交互，超出本次范围。后果（已记入「未覆盖」）：页面可见时间（活动时间）可能与结构化数据的 `datePublished`（发布时间）不同。

### 3.4 判定规则（改后）

| 上游情况 | kind | 页面结果 |
|---|---|---|
| HTTP 404 | `notFound` | `notFound()` → 404 + noindex（唯一允许的 404 来源） |
| 其它非 2xx（429 / 403 / 5xx） | `httpError` | 抛错 → error.tsx / 500 |
| HTTP 2xx 但 `code !== 0` | `invalidPayload` | 抛错 → 500 |
| 超时 | `timeout` | 抛错 → 500 |
| 网络异常 | `networkError` | 抛错 → 500 |
| 2xx 且业务成功 | `ok` | 正常渲染 |

### 3.6 这次新踩的坑

1. **行尾**：工作树文件是 CRLF，而 PowerShell here-string 构造的锚点是 LF，`String.Contains` 直接匹配失败（第一次报 `anchor count=0`）。改为「读入后统一转 LF 比较，写回时按原文件风格还原」，避免整文件行尾 diff。
2. **JS 模板字面量里的反引号**：补丁脚本整体放在 JS 模板字符串中，而目标代码含反引号模板字符串，会提前终止外层字面量（报 `Unexpected number`）。对满屏反引号的文档类补丁，改用字符 ` 作占位符，写完再统一替换成反引号。
3. **PowerShell 嵌套数组扁平化**：`@( @('a','b',1) )` 会被展开成扁平数组，导致 `$pair[1]` 变成 `[char]` 并报「[System.Char] 不包含 Replace」。改成显式参数逐个传递。
4. **行为等价必须逐字保留**：`getApiData` 的重试语义是不对称的（5xx 才重试、4xx 立刻返回、异常一直重试到耗尽、重试恢复打 warn），日志分支由 `warnStatuses / warnOnFailure` 控制。重写时必须逐字保留，否则 8 个旧调用方的行为与日志都会漂移。
5. **构建期故障面变大（有意接受）**：`/app/[id]` 是全仓唯一带 `generateStaticParams` 的页面（100 个 SSG 页）。改成「故障即抛错」后，构建期任何上游 5xx / 超时都会让 `pnpm build` 直接失败，不再像以前那样静默产出 404 页。本次实测 100 页全部成功、build 退出 0。取舍：构建失败优于把有效 URL 发布成永久 noindex 的 404；代价是构建对后端可用性更敏感。
6. **`not-found.tsx` 的 noindex 是放大器根因**，但审计已判定该文件本身不需要改，本次未动它 —— 修的是调用方判据。
